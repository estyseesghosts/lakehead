# Architecture and ownership

## Active Home row contract (grid repair)

`lakehead-grid-repair-plan.md` supersedes the historical signed/rebased Home movement plan. Phase 1 (completed, reviewed 2026-10-05) establishes permanent logical row/column zero, nonnegative persisted coordinates, horizontally bounded but vertically unbounded placement legality, and content extent `max(row + rowSpan)` measured from row zero. Leading empty rows remain real, including through repository gap normalization. Viewport/edit workspace height controls presentation and scroll reachability, never logical legality. `:core:grid` owns these rules; repository boundaries own normalization; Home consumes absolute placements. Shared signed/windowed primitives may remain for other callers, but are not the target Home contract. Later repair phases, not Phase 1, replace geometry, gestures, rendering virtualization and persistence acknowledgements.

The full frozen Home grid contract is `../lakehead-grid-repair-plan.md` §3 and `design.md` "Frozen Home grid contract". Architecture-relevant consequences:

- One geometry owner. A single immutable metrics object owns every logical↔pixel transform for Home. Rendering, hit testing, move, resize and overlays consume it; no second formula lives in a feature, and geometry math carries no Compose state.
- One gesture, one route. After slop a drag is MOVE or RESIZE until release/cancel. MOVE preserves span and RESIZE preserves position as state invariants, not late validation.
- Legality stays in `:core:grid`: nonnegative row and column, horizontal fit within `columns`, positive span, rectangle collision. Pixel geometry and viewport size never decide legality.
- Persistence sits above the grid. Gestures emit a commit intent on release; the state owner calls the repository and reconciles from the accepted normalized placement set. No sequence IDs, leases or acknowledgement DTOs cross the grid boundary.
- Edit workspace height is presentation only — it sizes scrollable content and can never make a cell legal or illegal.

Retired, not to be reintroduced: negative persisted Home rows, drag-time origin animation, Home row-window rendering, clamped candidate cells, edit-legality frontiers, and persistence acknowledgement leases. Signed/windowed shared primitives survive only while another production caller needs them and are on the Phase 9 deletion list.

The included Gradle modules are real boundaries for the first milestone. Additional owners listed below become modules when implementation needs them; do not create empty modules solely to populate the tree.

Dependency direction: `app → feature → core` and `app → platform → core`; `core:grid → core:model`. Platform implementations never enter `core:model` or Compose state. Feature-to-feature implementation dependencies are prohibited. Application wiring joins feature contracts to platform/data implementations. Each state stream has one owner: installed-app inventory and symbol snapshots in platform, persisted arrangement in data, transient gesture state in feature, and placement rules in grid. Icon extraction, decoding, and normalization never occur in composables or tile composition; features render pre-resolved snapshots only.

Free placement vs filtered packing: normal Home editing preserves holes and unrelated tile positions and never auto-compacts, sorts, packs toward top-left, requires complete rows, or fills empty cells. Empty cells are transparent wallpaper, not placeholders, and grid lines are never rendered. Narrow exception: repository transaction boundaries may normalize only completely empty gaps greater than two rows after an accepted place/move/resize/remove or while loading; this shifts whole occupied sections upward while retaining order, columns, spans and IDs, and is not a drag-preview rule. Deterministic bottom-weighted packing exists only as a separate generated-projection API over `:core:grid` (Show All Apps / Show All Widgets style views); it must not mutate source Homes and must not leak into normal edit legality. Keep `FreePlacementEngine` and filtered-packing responsibilities separate even before separate files become worthwhile.

Spans are generic: persistence and the grid data model store positive integer column/row spans, not a `SMALL`/`MEDIUM`/`LARGE` enum. The B1 `SUPPORTED` allowlist (1×1, 2×1, 1×2, 2×2, 4×2) is a phase-limited legality gate, not the data model. `docs/grid.md` adds 3×2, 4×3, and 3×3 as valid examples of the open set. Generalize `GridRules` legality to bounds + rectangle collision before claiming F3 expanded tiles beyond the B1 set; renderable-size policy then belongs to UI/editing slices, not to a grid allowlist rejection.

Design-system primitives describe reusable geometry and small layout contracts; feature screens own arrangement. A screen can place navigation, controls, overlays and other elements through explicit anchors/regions/insets and measured geometry (such as bottom, top, side or floating), without assuming fixed coordinates or a bottom navigation bar. Shared `LauncherDimensions` tokens (grid gap, horizontal inset, tile padding, symbol size) govern every tile size; a multi-cell tile is exactly its cells plus internal gaps. The five-column layout is a normal-phone reference arrangement, not a fixed screen contract; arrangement and grid width are inputs that can vary across screen shapes while stable logical content is retained. Rendering uses a dedicated absolute-coordinate layout from logical cells, never `LazyVerticalGrid` and never `Column { Row { } }`, and places each tile at its absolute logical row. The grid-owned row window still exists for shared callers, but **Home does not use it and must not rebase distant rows** — under the frozen contract a tile at row N renders from row N whatever else is occupied (repair plan Slice 5.5). These contracts must not implement another placement or packing system: `:core:grid` remains the sole owner of placement legality, extent and projection. B3 remains pure count adaptation.

Tile interaction and appearance: home tiles keep placement, appearance (`TileColorRole.Normal` / `Accent` resolved to Material dynamic colors on API 31+ with a static fallback palette only), content (profile-aware app reference), and interaction map (`TileHitTarget.Body` / `AppSymbol` / `Shortcut(index)`) as separate concepts. `Body` and `AppSymbol` both launch today but remain separate hit regions so `Body` can later open the notification surface without geometry rework. App-list rows use sibling launch vs shortcut regions, never one parent clickable containing nested buttons. Shortcut slots render only configured shortcuts; the default is an empty list with no placeholder controls. Symbol placement is bottom-right for small tiles except 1×2 bottom-center; a large zero-pin tile centers the symbol at the minimum available width/height after padding, with no strip reserve; see `docs/grid.md` §4. Diagnostic mockup colors are never layout concepts; use semantic `TileBody` / `AppLaunchButton` / `ShortcutSlot` names.

Planned ownership: `core:navigation` for destination state; `data:database` for pages, placements, folders, rules and history (future logical tile configuration: `TileAppearance` color role + `ConfiguredShortcut` slots via explicit migration, never speculative fields); `data:preferences` for settings; `data:repository` for domain-facing data operations; `platform:shortcuts`, `widgets`, `notifications`, `usage`, `contacts`, `documents` each own their Android gateway; `:platform:widgets` owns `AppWidgetHost` / `AppWidgetManager` and is being introduced per `docs/agents/tasks/widgets.md`; planned `platform:privileged` owns the Shizuku-gated privileged package-state backend behind a domain interface, and planned `platform:shelter` owns Shelter detection plus unfreeze-and-launch resolution; app-symbol pipeline stays in `:platform:launcherapps` until a dedicated `platform:symbols` split is justified (source resolver → normalization → bounded cache → Home + list + search + folders); `allapps`, `search`, `messages`, `editing`, `settings`, `news` own their UI/use cases; folders live in `:feature:home` per `docs/agents/tasks/folders.md`. `benchmark` owns startup measurements; `build-logic` owns conventions once repetition justifies it. New Gradle modules are added only when real privileged/Shelter code needs the boundary, never as empty directories.

Optional Shelter mode (Shizuku-gated): Shelter integration is an optional capability layer, never the default catalogue behavior. Baseline launcher behavior without Shizuku is unchanged: `:platform:launcherapps` remains the inventory, `LauncherApps.startMainActivity` remains the launch path, and `LauncherApps.Callback` remains the invalidation signal. Shelter mode is considered activated only while the privileged backend reports ready: Shizuku Binder received plus runtime permission granted (`PrivilegeState.Ready`, backend ADB or root). A stored user preference records only that the user wants the integration; it is never treated as proof of current access. Binder death, denied permission, stopped Shizuku, or reboot immediately falls back to baseline with no stale ready state. Shizuku permission is never requested at startup; it is requested from explicit enhanced-access UI or on first attempt of a Shizuku-only operation.
- Catalogue identity: `core:model` owns the stable identity `(packageName, ProfileId)` already expressed as `core/model/src/main/java/me/foxtails/lakehead/core/model/AppIdentity.kt:4` plus `ProfileId.kt:10`, and the future persistent record (`AppRecord`: packageName, profile, launch component, label, symbol, placement, `AppAvailability`: `AVAILABLE` / `SHELTER_FROZEN` / `PROFILE_PAUSED` / `UNINSTALLED`). When a `LauncherApps` entry disappears, placement is never deleted immediately. If the identity was previously known in the Shelter work profile, the disappearance is resolved through the privileged package-state interface (`isInstalled` / `isHidden` / `listPackages(includeHidden)` for the work-profile user): still installed plus hidden becomes `SHELTER_FROZEN` with placement unchanged; no longer installed becomes `UNINSTALLED`. Cold start recovers never-seen frozen apps by unioning normal `LauncherApps` enumeration with privileged enumeration and creating `SHELTER_FROZEN` records from cached package/label/APK/symbol/component/profile data.
- Launch routing: `AVAILABLE` uses `LauncherApps.startMainActivity` under the correct profile. `SHELTER_FROZEN` prefers Shelter's public `net.typeblog.shelter.action.PUBLIC_UNFREEZE_AND_LAUNCH` via `net.typeblog.shelter.ui.DummyActivity` so Shelter retains auto-freeze bookkeeping, and uses privileged unhide (`pm hide/unhide --user`) plus delayed `startMainActivity` only as fallback when Shelter is absent. `PROFILE_PAUSED` keeps separate work-profile-paused handling. UI code sees only a sealed launch action (`Normal` / `ShelterUnfreeze` / `ShizukuUnfreeze`); it never knows about Shelter intents, `DevicePolicyManager`, Shizuku Binder, or shell commands.
- Presentation parity: a Shelter work-profile app, frozen or available, is a first-class tile like any other app. Home, folders, All Apps, and search continue to find it; grid placement, persistence, and filtered-packing rules are unchanged; a freeze must never trigger compaction, reflow, or placement destruction. All configured tile hit targets keep working, including shortcut buttons (`TileHitTarget.Body` / `AppSymbol` / `Shortcut(index)` on Home and sibling launch vs shortcut regions in the app list): invoking a shortcut on a `SHELTER_FROZEN` record routes through the same unfreeze-then-deliver path rather than hiding the shortcuts. The only permitted frozen difference is a small presentation state indication (for example a badge or reduced opacity).
- Dependency direction: `feature/*` and most of `core/*` never import `rikka.shizuku.*`. One application-scoped privileged controller converts Binder-received/death plus permission-result callbacks into `StateFlow<PrivilegeState>`; capability checks (`PACKAGE_CONTROL`, `CROSS_USER_PACKAGE_QUERY`, per-operation support) are separate from availability because ADB vs root backends differ by version/OEM. Privileged operations are narrow typed methods, never a generic shell executor; simple calls may use the Binder wrapper while larger privileged logic belongs in a Shizuku `UserService`. Full contracts live in `docs/shizuku.md` and `docs/shelter.md`; this section records only ownership, activation, and parity rules.

Decomposition triggers: notification ingestion → parsing → conversation detection → normalization → storage → classification; search query fan-out → individual providers → result ranking; grid geometry → free-placement validation vs filtered packing → edit validation; app catalogue enumeration → symbol source resolution → normalization → bounded cache → callback invalidation → launching. Keep these separate responsibilities even before separate modules become worthwhile. Files are split for ownership or dependencies, never merely for length.

Implementation order: 0A foundation, 0B HOME/`LauncherApps`, 1A grid engine/tests, 1B custom components, 1C persisted home/editing, 1D folders, then optional S1 Shelter mode (Shizuku-gated, after persisted placement exists; does not block 1C/1D and does not change baseline without Shizuku permission). See `docs/agents/tasks/foundation.md` for progress and `docs/first_draft.md` for the S1 exit gate.
