# Architecture and ownership

The included Gradle modules are real boundaries for the first milestone. Additional owners listed below become modules when implementation needs them; do not create empty modules solely to populate the tree.

| Module | Ownership |
| --- | --- |
| `:fixtures:launchable` | Source-free Android test infrastructure: isolated installable launchable-activity fixture for real package add/remove validation; no production module depends on it |
| `:app` | Android application entry point and composition wiring; no platform catalogue or grid logic |
| `:core:model` | Stable domain identities and launcher item models; no Android service objects or Compose types |
| `:core:grid` | Sole owner of free-placement legality (bounds + rectangle collision), vertical extent, row-window selection, and viewport/count adaptation, plus a separate deterministic filtered-packing projection; no item rendering and no auto-compaction of normal Home placement. Visual/interaction authority: `docs/grid.md` + `docs/grid/` photos |
| `:core:designsystem` | Reusable custom Compose launcher primitives, shared symbol-rendering boundary (draws pre-resolved snapshots only), and small reusable geometry/layout contracts; no repository access or screen-specific arrangement |
| `:platform:launcherapps` | Profile-aware Android `LauncherApps` inventory, callbacks and launch APIs; owns app-symbol source resolution (monochrome > adaptive foreground > legacy fallback), normalization, and bounded snapshot cache keyed by full `AppIdentity`; translates Android types to domain |
| `:feature:home` | Home screen UI state, gestures, screen-specific arrangement and tile hit-target dispatch (`Body` / `AppSymbol` / `Shortcut(i)` as separate regions); depends on grid rather than implementing placement |
| `:feature:allapps` | App-list presentation with sibling launch vs shortcut hit targets and shared symbol pipeline; no catalogue logic in UI |

Dependency direction: `app → feature → core` and `app → platform → core`; `core:grid → core:model`. Platform implementations never enter `core:model` or Compose state. Feature-to-feature implementation dependencies are prohibited. Application wiring joins feature contracts to platform/data implementations. Each state stream has one owner: installed-app inventory and symbol snapshots in platform, persisted arrangement in data, transient gesture state in feature, and placement rules in grid. Icon extraction, decoding, and normalization never occur in composables or tile composition; features render pre-resolved snapshots only.

Free placement vs filtered packing: normal Home editing preserves holes and unrelated tile positions and never auto-compacts, sorts, packs toward top-left, requires complete rows, or fills empty cells. Empty cells are transparent wallpaper, not placeholders, and grid lines are never rendered. Deterministic bottom-weighted packing exists only as a separate generated-projection API over `:core:grid` (Show All Apps / Show All Widgets style views); it must not mutate source Homes and must not leak into normal edit legality. Keep `FreePlacementEngine` and filtered-packing responsibilities separate even before separate files become worthwhile.

Spans are generic: persistence and the grid data model store positive integer column/row spans, not a `SMALL`/`MEDIUM`/`LARGE` enum. The B1 `SUPPORTED` allowlist (1×1, 2×1, 1×2, 2×2, 4×2) is a phase-limited legality gate, not the data model. `docs/grid.md` adds 3×2, 4×3, and 3×3 as valid examples of the open set. Generalize `GridRules` legality to bounds + rectangle collision before claiming F3 expanded tiles beyond the B1 set; renderable-size policy then belongs to UI/editing slices, not to a grid allowlist rejection.

Design-system primitives describe reusable geometry and small layout contracts; feature screens own arrangement. A screen can place navigation, controls, overlays and other elements through explicit anchors/regions/insets and measured geometry (such as bottom, top, side or floating), without assuming fixed coordinates or a bottom navigation bar. Shared `LauncherDimensions` tokens (grid gap, horizontal inset, tile padding, symbol size) govern every tile size; a multi-cell tile is exactly its cells plus internal gaps. The six-column phone layout is a normal-phone reference arrangement, not a fixed screen contract; arrangement and grid width are inputs that can vary across screen shapes while stable logical content is retained. Rendering uses a dedicated absolute-coordinate layout from logical cells, never `LazyVerticalGrid` and never `Column { Row { } }`; the sparse/windowed layout composes only visible/near-visible placements through the grid-owned row window and rebases distant rows without allocating intervening empty rows. These contracts must not implement another placement or packing system: `:core:grid` remains the sole owner of placement legality, extent and projection. B3 remains pure count adaptation.

Tile interaction and appearance: home tiles keep placement, appearance (`TileColorRole.Normal` / `Accent` resolved to Material dynamic colors on API 31+ with a static fallback palette only), content (profile-aware app reference), and interaction map (`TileHitTarget.Body` / `AppSymbol` / `Shortcut(index)`) as separate concepts. `Body` and `AppSymbol` both launch today but remain separate hit regions so `Body` can later open the notification surface without geometry rework. App-list rows use sibling launch vs shortcut regions, never one parent clickable containing nested buttons. Shortcut slots render only configured shortcuts; the default is an empty list with no placeholder controls. Symbol placement is bottom-right except 1×2 bottom-center, expressed as one generic rule that survives new spans. Diagnostic mockup colors are never layout concepts; use semantic `TileBody` / `AppLaunchButton` / `ShortcutSlot` names.

Planned ownership: `core:navigation` for destination state; `data:database` for pages, placements, folders, rules and history (future logical tile configuration: `TileAppearance` color role + `ConfiguredShortcut` slots via explicit migration, never speculative fields); `data:preferences` for settings; `data:repository` for domain-facing data operations; `platform:shortcuts`, `widgets`, `notifications`, `usage`, `contacts`, `documents` each own their Android gateway; app-symbol pipeline stays in `:platform:launcherapps` until a dedicated `platform:symbols` split is justified (source resolver → normalization → bounded cache → Home + list + search + folders); `feature:folders`, `allapps`, `search`, `messages`, `editing`, `settings`, `news` own their UI/use cases. `benchmark` owns startup measurements; `build-logic` owns conventions once repetition justifies it.

Decomposition triggers: notification ingestion → parsing → conversation detection → normalization → storage → classification; search query fan-out → individual providers → result ranking; grid geometry → free-placement validation vs filtered packing → edit validation; app catalogue enumeration → symbol source resolution → normalization → bounded cache → callback invalidation → launching. Keep these separate responsibilities even before separate modules become worthwhile. Files are split for ownership or dependencies, never merely for length.

Implementation order: 0A foundation, 0B HOME/`LauncherApps`, 1A grid engine/tests, 1B custom components, 1C persisted home/editing, 1D folders. See `docs/agents/tasks/foundation.md` for progress.
