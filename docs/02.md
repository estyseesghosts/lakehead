# Task Specification

## Objective

Fix and complete these four launcher areas:

1. Tile touch-target behavior.
2. Tile resizing.
3. Pinned shortcut rendering and interaction.
4. Feed integration diagnosis and repair.

Stay within this scope. Do not use this task as an excuse for unrelated launcher redesign or broad refactoring.

---

# 1. Tile Interaction Model

## Required behavior

Treat each tile as **one cohesive surface containing multiple independent tap targets**.

A tile may contain:

- Main app icon.
- Pinned shortcut icons.
- Future notification area.
- Edit-mode controls.

### Short taps

Short taps must continue to act on the specific target under the pointer.

Examples:

- App icon → launch the app.
- Shortcut icon → launch that shortcut.
- Future notification area → perform its own action.

### Long press

A long press anywhere inside the tile must belong to the tile itself.

It must work when started on:

- Main app icon.
- Pinned shortcut.
- Empty tile area.
- Any other interactive child region.

A child composable must not consume the gesture in a way that prevents the tile-level long press.

Once edit mode starts, the tile must behave as one draggable unit.

## Investigation steps

1. Trace pointer handling from the tile root through every interactive child.
2. Identify where tap, long-press, and drag events are currently consumed.
3. Inspect competing `clickable`, `combinedClickable`, `pointerInput`, drag, or gesture modifiers.
4. Determine whether child interaction modifiers block long-press handling at the tile level.
5. Establish one clear ownership model:
   - child owns short tap,
   - tile owns long press,
   - tile owns edit-mode dragging.
6. Verify this on:
   - tiles without shortcuts,
   - tiles with one shortcut,
   - tiles with several shortcuts,
   - tiles with unused empty space.

## Acceptance tests

- Long-press main app icon → tile enters edit mode.
- Long-press pinned shortcut → tile enters edit mode.
- Long-press empty tile area → tile enters edit mode.
- Short-tap app icon → app launches; edit mode does not start.
- Short-tap shortcut → shortcut launches; app does not launch.
- Enter edit mode from any point on the tile, then drag → entire tile moves.
- No special empty area or hidden grab region is required.

# 2. Tile Resizing

## Required behavior

Use the existing bottom-right `>` resize control as the resize interaction point.

The current behavior is incomplete: resize mode can be enabled, but the actual resize gesture is difficult or inconsistent to start.

### State behavior

When resize mode is **off**:

- Tap the resize button.
- Resize mode becomes enabled.

When resize mode is **on**:

- The same resize button becomes the resize drag handle.
- Pressing and dragging that handle starts resizing.
- Starting the drag must **not** toggle resize mode off.
- Releasing the pointer ends that resize gesture.
- Resize mode remains active until existing edit-mode rules explicitly exit it.

The visible control can remain visually small, but its effective touch target must be large enough for reliable touch input.

Once a resize gesture starts, continue tracking the pointer even when it leaves the original handle bounds.

## Investigation steps

1. Find the current owner of resize-mode state.
2. Find the resize button click handler.
3. Find the existing resize drag detector.
4. Determine why resize mode activates but resize dragging is unreliable.
5. Specifically check whether:
   - click and drag handlers compete,
   - drag detection is attached to the wrong composable,
   - the hit region is too small,
   - parent tile gestures consume the pointer,
   - resize mode toggles on pointer-down instead of a completed tap.
6. Make the resize button itself the reliable resize drag origin.
7. Clearly separate:
   - tap-to-enable,
   - drag-while-enabled.
8. Preserve existing size limits and collision rules unless investigation proves they are defective.

## Acceptance tests

- Tap resize button once → resize mode activates.
- Press and drag the same button → tile starts resizing.
- Starting that drag does not disable resize mode.
- Slow drag works.
- Fast drag works.
- Diagonal drag works where tile sizing rules permit it.
- Resize continues after the pointer moves outside the visible button.
- Repeated resize attempts do not require pixel-perfect placement.
- Pointer release stops the active resize gesture cleanly.
- Tile does not accidentally move instead of resize.

# 3. Pinned App Shortcut Rendering

## Required behavior

Shortcut discovery and shortcut pinning appear to already exist.

Do not replace that subsystem unless investigation shows that it is fundamentally unusable.

The work here is to correctly render and interact with pinned shortcuts inside tiles.

## Layout rules

Treat each logical `1x1` portion of a tile as one icon position.

The main app icon occupies one position.

The remaining positions can contain pinned shortcuts.

### No pinned shortcuts

When a tile has no pinned shortcuts:

- Preserve the existing large centered app-icon behavior.
- Do not force the app icon into the bottom-right corner.

### One or more shortcuts pinned

As soon as at least one shortcut is pinned:

- Move the main app icon to the tile's bottom-right icon position.

For a horizontal or square tile:

```text
[ shortcut ][ shortcut ][ app ]
```

Pinned shortcuts extend leftward from the app icon.

For a vertical tile:

```text
[ shortcut ]
[ shortcut ]
[   app    ]
```

Pinned shortcuts extend upward from the app icon.

## Orientation rule

Derive layout from the tile geometry rather than hard-coding every tile size.

General rule:

- `width >= height` → horizontal progression.
- `height > width` → vertical progression.

If the existing launcher already contains a more precise compatible rule, keep it.

## Capacity

Do not render more icon targets than the tile can contain.

Expected model:

```text
available icon positions ≈ number of 1x1 cells
shortcut capacity = positions - 1 app-icon position
```

Handle excess pinned shortcut data safely.

Do not overlap icons or place them outside tile bounds.

## Interaction requirements

- Main app icon → launch main app.
- Shortcut icon → launch that shortcut.
- Each shortcut remains an independent tap target.
- Long-pressing the app icon still enters tile edit mode.
- Long-pressing a shortcut still enters tile edit mode.
- Moving the tile in edit mode moves all tile contents together.

## Investigation steps

1. Locate existing shortcut persistence/state.
2. Confirm whether pinned shortcuts are already stored correctly.
3. Confirm whether shortcut launch intents already work.
4. Locate the current tile-content renderer.
5. Find the existing "large centered icon when no shortcuts exist" behavior.
6. Extend that renderer instead of creating a second tile implementation.
7. Derive shortcut slots from tile dimensions.
8. Verify shortcut ordering is deterministic and stable.
9. Verify layout updates immediately when:
   - the first shortcut is pinned,
   - another shortcut is pinned,
   - a shortcut is removed,
   - the final shortcut is removed.

## Acceptance tests

### No shortcuts

- Large tile with zero shortcuts → app icon remains centered and enlarged.

### Horizontal or square tile

- Pin one shortcut → app icon moves bottom-right.
- Shortcut appears immediately to its left.
- Additional shortcuts continue leftward.
- Icons do not overlap.

### Vertical tile

- Pin one shortcut → app icon occupies the bottom position.
- Shortcut appears directly above it.
- Additional shortcuts continue upward.

### Interaction

- Tap app icon → app opens.
- Tap shortcut → correct shortcut opens.
- Long-press app icon → tile enters edit mode.
- Long-press shortcut → tile enters edit mode.
- Remove final shortcut → tile returns to centered app-icon layout.

# 4. Feed Integration

## Problem statement

Testing has only produced the `feed unavailable` state.

Do not assume the feed implementation is functional just because failure is handled cleanly. Determine the actual cause.

The intended supported feed paths remain:

- Google feed through the existing AIDLBridge-compatible integration.
- Neo Feed.

## Required investigation order

### Step 1: Test the build-type hypothesis

First determine whether feeds fail because testing has only used debug builds.

Compare:

- Debug build.
- Appropriate release or release-equivalent build.

Check for differences in:

- Application ID.
- Signing certificate.
- Package visibility.
- Permissions.
- Provider allowlists.
- Binder/service permissions.
- Provider caller expectations.
- Manifest configuration.
- ProGuard/R8 behavior, if relevant.

Do not conclude that signing or build type is the cause without evidence.

### Step 2: Trace provider discovery

Verify:

- Is the provider installed?
- Does the launcher discover it?
- Which package/component is found?
- Does compatibility validation pass?
- If validation fails, what exact check fails?

Expose the real diagnostic state during development instead of reducing everything to `feed unavailable`.

### Step 3: Trace service binding

Verify:

- Is a bind attempted?
- Does Android resolve the target service?
- Does binding succeed?
- Is a binder returned?
- Does the provider reject the launcher?
- Does the binder disconnect immediately?

Capture the exact failure point.

### Step 4: Trace protocol setup

Follow the complete path:

```text
launcher
→ provider discovery
→ provider validation
→ bind request
→ binder connection
→ AIDLBridge/feed handshake
→ feed surface/session creation
→ feed rendering
```

Identify the **first** stage that fails.

### Step 5: Validate both intended provider paths

Do not test one provider and generalize the result to the entire feed subsystem.

Where the test environment allows it, check:

- Google-feed provider path.
- Neo Feed path.

A provider-specific failure must remain distinguishable from a launcher-wide feed failure.

## Required diagnostics

During development, the implementation must distinguish at least these states:

- No provider installed.
- Provider not discoverable.
- Provider rejected.
- Service not resolvable.
- Bind failed.
- Binder disconnected.
- Protocol negotiation failed.
- Feed surface/session creation failed.
- Feed rendering failed.

The production UI can remain simple. The internal diagnostic path cannot remain a single generic failure state.

## Acceptance tests

### Build type

- Debug behavior is explicitly tested.
- Release or release-equivalent behavior is explicitly tested.
- Any difference is documented with the actual cause.

### Discovery

- Compatible provider is detected.
- Correct package/service/component is selected.

### Binding

- Launcher successfully binds to at least one intended compatible provider.

### Feed operation

- Feed session or surface is created successfully.
- Actual feed content becomes visible in the launcher.
- Swiping to the feed page shows provider content rather than `feed unavailable`.

### Failure handling

With no provider installed:

- Launcher remains stable.
- Correct unavailable state is shown.
- Development diagnostics expose the actual reason.

With an incompatible or broken provider:

- Launcher does not crash.
- Failure is attributed to the correct stage.

# Cross-Cutting Requirements

## Gesture ownership

Do not solve one gesture problem by creating another.

Verify interactions between:

- Tile taps.
- Shortcut taps.
- Tile long press.
- Tile dragging.
- Resize dragging.
- Horizontal page swiping.

The existing rule remains: page-navigation gestures must not interfere with edit-mode interaction.

## Architecture

Do not concentrate all of this behavior into one large composable, controller, or gesture function.

Keep responsibilities separated between:

- Tile state.
- Tile rendering.
- Child target actions.
- Edit-mode gesture coordination.
- Resize state and resize gestures.
- Shortcut layout.
- Feed discovery and binding.
- Feed UI state.

Do not introduce new god-files or god-functions.

## Validation

Run the repository's normal available validation after implementation.

At minimum, run the relevant:

- Build.
- Unit tests.
- UI/instrumentation tests, where available.
- Static analysis/lint.

Add focused regression tests where the architecture makes that practical.

---

# Explicit Non-Goals

Do **not**:

- Redesign tile visuals.
- Redesign edit mode.
- Change the current grid-placement model.
- Add new tile sizes.
- Redesign the resize icon.
- Replace shortcut discovery without proving it is defective.
- Introduce a new shortcut persistence format without need.
- Implement the future notification area.
- Redesign the feed UI.
- Add new feed-provider types beyond the intended architecture.
- Replace AIDLBridge with a new protocol unless the current architecture is demonstrably incompatible.
- Change page navigation except where required to resolve gesture conflicts.
- Perform broad unrelated refactors.
- Hide feed failures behind the existing `feed unavailable` state without finding the cause.
- Declare feed work complete because failure handling is graceful.

---

# Completion Definition

The task is complete only when all of these are true:

1. A long press anywhere on a tile can enter tile edit mode.
2. App and shortcut short taps still work independently.
3. The resize button reliably becomes the resize drag handle after resize mode is enabled.
4. Beginning a resize drag no longer disables resize mode.
5. Pinned shortcuts render according to tile orientation and available `1x1` positions.
6. App and shortcut targets launch their correct actions.
7. Feed failure has been traced to a concrete cause.
8. At least one intended compatible feed provider successfully connects and displays content, **or** there is documented external evidence showing that a successful connection is impossible in the current test environment.
9. Relevant tests and repository validation pass.
10. No unrelated redesign or broad refactor was introduced.
