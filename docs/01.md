# Planning Requirements

Treat this as a **requirements brief**. Inspect the existing implementation, identify the relevant components and root causes, then produce an implementation plan. Do not preserve broken behavior for compatibility.

## 1. Repair feed overlays

- The feed-overlay system is currently non-functional. Investigate the complete feed connection and display path.
- Restore working support for:
  - **Google Feed through AIDLBridge**
  - **Neo Feed**
- Both providers must integrate with the launcher's existing left-side feed surface.
- Determine whether the failure is in provider discovery, binding, lifecycle, IPC, gesture/navigation integration, rendering, or another layer.
- Do not special-case one provider in a way that prevents other compatible feed providers from working.

## 2. Fix tile dragging and separate it from resizing

The attached video shows the current drag interaction is incorrect.

### Observed bug

While attempting to move a selected tile:

- The tile does not freely translate around the two-dimensional grid.
- Movement is effectively constrained to horizontal changes.
- Vertical movement does not produce normal row-to-row repositioning.
- Dragging also changes the tile's grid footprint. The tile switches between narrower and wider shapes while it is being moved.
- The tile therefore behaves as if **move, resize, and grid reflow are incorrectly coupled together**.
- The tile's position/shape snaps between layouts instead of following the intended free grid placement.

### Required behavior

Moving and resizing must be separate interaction states.

- Normal edit-mode dragging means **move only**.
- Moving a tile must preserve its current width and height.
- A tile must be movable to any valid free position in both X and Y.
- Placement must obey collision and grid-boundary rules.
- Do not restrict dragging to the current row.
- Do not implicitly resize a tile because the pointer crosses another grid cell.
- Resizing must not begin until the user explicitly taps the tile's **resize-arrow button**.
- After resize mode starts, the existing drag-to-resize interaction can be used.

The planner should identify where gesture interpretation, tile geometry, collision checking, and placement state became coupled and design a clean separation between:

1. tile selection,
2. tile movement,
3. resize-mode activation,
4. tile resizing.

## 3. Dynamic grid height and scrolling

The tile grid must expand and contract based on occupied content.

### Normal mode

- Track the minimum and maximum occupied vertical grid coordinates.
- If every tile fits inside the usable navigation-safe area, keep the grid within that area.
- In this state, the home screen must **not scroll**.
- Do not expose empty scrollable space below the last required row.
- If occupied tiles extend below the safe area, enable vertical scrolling.
- The scrollable extent should correspond to the actual tile area, not an arbitrary fixed-height grid.

### Edit mode

Edit mode is different:

- The grid must always permit downward expansion.
- The user must be able to drag a tile below the current occupied area into new empty rows.
- Therefore, the grid must remain vertically extendable/scrollable while editing.
- Dragging near or into lower available space must allow the viewport/grid to advance downward.
- After editing ends, recompute the occupied range.
- If the resulting layout fits inside the safe area again, collapse the extra extent and disable scrolling.
- If it remains larger than the safe area, retain normal scrolling.

Conceptually:

**normal mode:** content-sized grid, scrolling only when required.  
**edit mode:** temporarily extensible grid with room to create additional rows.

## 4. Work-profile app naming and sorting

Work-profile apps need a display prefix without changing their sort position.

Example:

- Real app label: `Firefox`
- Display label: `Work Firefox`
- Sort key: `Firefox`

Requirements:

- Sort work-profile apps by the application's original label.
- Apply the profile prefix **after determining the sort key**.
- The visible prefix must never affect alphabetical grouping or ordering.
- Do not hardcode `"Work"` into the app-list implementation.
- Model the prefix/profile presentation separately because later Shelter integration will use a different label, such as `"Shelter"`.
- The design should allow other profile/source labels without modifying sorting logic.

## 5. Edit-mode unpin button placement

Change `(×)` button placement based on tile dimensions.

- `1×1`: top-right corner.
- `1×2`: top-right corner.
- `2×1`: top-right corner.
- Any larger tile: centered inside the tile.

The button must remain associated with the tile while moving or resizing.

## 6. Make Android app shortcuts functional

The current shortcut UI is not functional. Replace or repair it as necessary.

### Opening shortcuts

- Long-pressing a tile enters edit mode and selects that tile.
- Once edit mode is active, show the selected application's available Android app shortcuts.
- Tapping another tile while remaining in edit mode changes the selected tile.
- The shortcut list must update to show the newly selected application's shortcuts.
- The user must not need to leave and re-enter edit mode for each tile.

This means edit mode has a persistent **selected tile/application** concept.

### Shortcut functionality

- Retrieve the actual shortcuts exposed by the selected application.
- Show available shortcut actions in the edit UI.
- The actions themselves must be functional, not placeholder entries.
- Handle applications with no shortcuts cleanly.
- Account for shortcut data changing while the launcher is running.

## 7. Add shortcut pinning after shortcut execution works

Do this only after the base shortcut system works correctly.

Each shortcut shown in the shortcut list must have a **pin-action control** beside it.

Activating it pins that shortcut to the selected tile.

Keep these concepts separate:

- the application represented by the tile,
- an application's available shortcuts,
- shortcuts pinned to that specific tile.

Pinned-shortcut state must therefore belong to the tile/layout model, not globally to the application.

## 8. Large-tile icon layout before shortcuts are pinned

For tiles larger than `1×2` / `2×1`:

- If the tile contains **no pinned shortcuts**, use the application as the primary visual content.
- Scale the application icon substantially larger than the current small large-tile icon.
- Center it in the tile.
- Let it occupy most of the available tile area while preserving normal padding and aspect ratio.

Do not reserve empty shortcut space when no shortcuts are pinned.

## 9. Layout of pinned shortcuts

Use the attached mockup as the structural reference, with one correction: the horizontal examples in the mockup are too right-justified.

### Horizontal and square tiles

When shortcuts are pinned:

- Place the application icon and pinned shortcut icons along the **bottom horizontal edge**.
- Center the complete icon group horizontally within the tile.
- Keep consistent spacing between icons.
- The group must not be right-aligned as shown in parts of the rough mockup.

Required capacity examples:

- `2×2`: application icon + **1 shortcut**
- `2×4`: application icon + **3 shortcuts**

The planner should derive a general capacity/layout rule from tile dimensions instead of implementing only these two literal sizes.

### Vertical tiles

For a vertical tile:

- Keep the primary application icon at the **bottom-right**.
- Place pinned shortcut icons above it.
- Additional shortcuts extend upward along the tile's right edge.
- Preserve consistent padding and icon spacing.

### General behavior

- Resizing a tile must cause its pinned-shortcut layout to recompute.
- Do not allow shortcut icons to overlap edit controls.
- Define what happens if a tile is resized to a size that cannot contain all currently pinned shortcuts.
- The primary application icon must remain visually distinct from shortcut icons.

## 10. Required implementation order

Plan these as related but separable work items:

1. Repair feed overlays.
2. Correct move-vs-resize gesture/state handling.
3. Implement dynamic grid extent and scrolling.
4. Correct work-profile naming/sorting.
5. Correct edit-control placement.
6. Make app-shortcut discovery/display/launch functional.
7. Add shortcut pinning and persistence.
8. Implement responsive tile icon/shortcut layouts.
9. Add regression tests for grid movement, resizing, scrolling, profile sorting, shortcut selection, and pinned-shortcut layout.

The tile work should be designed around explicit state rather than adding more overlapping gesture conditions.
